## 为什么需要上线前自查？

很多团队上线后才发现：
- 监控没配，出了问题不知道
- 回滚不了，只能硬扛
- 被攻击了，没有防护
- 性能太差，用户流失
- 成本爆炸，预算超标

这份清单帮你**在上线前发现所有隐患**。

---

## 一、操作卓越性（保障上线与运维流畅）

### 1.1 事件响应计划

**必须明确：**

| 项目 | 内容 |
|------|------|
| **事件分级** | P0（核心功能不可用）、P1（重要功能异常）、P2（一般问题）、P3（轻微问题） |
| **责任人** | 每个级别对应谁处理 |
| **升级路径** | 一线运维 → 技术负责人 → 业务负责人 |
| **沟通渠道** | 内部群、用户公告页、客户成功团队 |
| **回滚触发条件** | 核心功能报错率 > 1%、服务不可用超 5 分钟 |

### 1.2 全链路监控

**必须覆盖：**

- **性能指标**：接口响应时间、页面加载速度
- **错误数据**：前端 JS 报错、后端 5xx/4xx 错误
- **流量波动**：QPS 峰值、用户地域分布

**工具推荐：**
- 前端：Sentry、Lighthouse
- 后端：Prometheus + Grafana
- 全链路：OpenTelemetry

### 1.3 部署与回滚能力

**上线前必须测试：**

- [ ] 灰度发布流程（10% 用户先行验证）
- [ ] 蓝绿部署流程（新旧版本无缝切换）
- [ ] 回滚操作可在 5 分钟内完成
- [ ] 回滚后数据一致性不受影响

### 1.4 构建效率优化（Monorepo 场景）

**配置项：**

- 依赖包缓存
- 子项目编译结果缓存
- 避免每次部署重复构建无变更模块

**目标：** 构建时长 ≤ 30 分钟

### 1.5 域名配置与迁移

**检查清单：**

- [ ] 添加 www 子域
- [ ] 设置顶级域名自动重定向到 www
- [ ] DNS 零停机迁移（先配新 DNS，等全球生效再停旧的）

## 二、安全性（防范上线后安全风险）

### 2.1 Web 应用防火墙（WAF）

**必须配置：**

- SQL 注入防护
- XSS 防护
- CSRF 防护
- 异常流量拦截（如单 IP 单日请求 > 1000 次触发挑战）

### 2.2 内容安全策略（CSP）

**配置项：**

```
Content-Security-Policy: 
  default-src 'self';
  script-src 'self' https://trusted-cdn.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
```

**禁止：**
- `inline-script`
- `unsafe-eval`

**必须添加的安全头：**
- `X-Frame-Options: DENY`
- `X-XSS-Protection: 1; mode=block`

### 2.3 环境访问控制

| 环境 | 访问控制 |
|------|----------|
| **测试/预发** | 密码验证 + 企业内网 IP 白名单 |
| **生产** | 禁止直接部署，需代码评审 + 测试验证 + 审批流程 |

### 2.4 日志与依赖安全

**日志：**
- 对接 ELK/Splunk
- 保留至少 30 天部署日志、访问日志

**依赖：**
- 提交依赖锁文件（`package-lock.json`、`pom.lock`）
- 配合 Snyk/Dependabot 扫描依赖风险

### 2.5 合规与权限

**SSL/TLS：**
- [ ] 证书未过期
- [ ] 域名匹配（泛域名覆盖所有子域）
- [ ] 支持 TLS 1.2+
- [ ] 禁用不安全加密套件

**权限：**
- [ ] 最小权限原则
- [ ] 移除离职人员账号
- [ ] 启用 SSO（SAML/OAuth2.0）
- [ ] 操作审计日志

**Cookie 合规：**
- [ ] 禁用不必要的第三方 Cookie
- [ ] 标记必要 Cookie 用途
- [ ] 符合 GDPR/CCPA

### 2.6 防范滥用

- 核心接口（登录、支付）实施速率限制（单用户 1 分钟 ≤ 10 次）
- 多租户应用添加「滥用举报入口」
- 后台可快速处理（封禁账号、删除内容）

## 三、可靠性（避免上线后服务中断）

### 3.1 冗余与故障切换

**核心服务：**
- 多区域节点部署
- 自动故障切换（某区域不可用 → 流量自动路由到其他区域）

**数据库/缓存：**
- 主从架构或集群模式
- 测试主从切换有效性（主节点宕机后，从节点 10 秒内接管）

### 3.2 缓存策略

| 资源类型 | 缓存策略 |
|----------|----------|
| **静态资源**（图片/CSS/JS） | 长期缓存（`max-age=31536000`）+ CDN |
| **API 响应** | 根据更新频率（实时不缓存、半实时缓存 5 分钟） |
| **静态页面** | ISR（定时重新生成，如新闻详情页 1 小时） |
| **动态数据** | 接口缓存（如用户个人信息） |

### 3.3 可观测性

**分布式跟踪：**
- 接入 OpenTelemetry
- 串联前端 → API → 数据库的请求链路

**负载测试：**
- 模拟 QPS 达预期峰值的 1.5 倍
- 验证上游服务承载能力

## 四、性能优化（提升用户体验）

### 4.1 核心性能指标

**前端（Core Web Vitals）：**

| 指标 | 目标 | 说明 |
|------|------|------|
| **LCP** | ≤ 2.5 秒 | 最大内容绘制时间 |
| **FID** | ≤ 100 毫秒 | 首次输入延迟 |
| **CLS** | ≤ 0.1 | 累积布局偏移 |

**后端（TTFB）：**

| 接口类型 | 目标 | 说明 |
|----------|------|------|
| **核心接口** | ≤ 300 毫秒 | 首页数据接口等 |
| **非核心接口** | ≤ 500 毫秒 | 设置页、帮助页等 |

### 4.2 资源加载优化

**图像：**
- 压缩体积（TinyPNG）
- 响应式尺寸（移动端 500px，PC 端 1000px）
- WebP/AVIF 格式
- 非首屏图像延迟加载

**脚本：**
- 代码拆分（路由懒加载）
- 按需加载非首屏脚本
- 禁用无意义第三方脚本
- 添加 `defer`/`async` 属性

**字体：**
- 字体子集（仅包含应用所需字符）
- 预加载关键字体
- `font-display: swap` 避免 FOIT

### 4.3 降低网络延迟

- 核心服务部署区域与目标用户匹配
- 避免多层代理（CDN → API 网关 → 后端）
- 必要时直接对接核心服务

## 五、成本优化（避免资源浪费）

### 5.1 成本构成梳理

| 资源类型 | 监控项 |
|----------|--------|
| **服务器实例** | CPU/内存使用率 |
| **CDN 流量** | 月流量、峰值带宽 |
| **对象存储** | 存储容量、请求次数 |
| **数据库** | 连接数、慢查询 |

**设置成本告警：** 月度支出超预算 10% 时触发通知

### 5.2 计算与存储优化

**计算资源：**
- 非核心接口超时设为 3 秒
- 低流量服务用 2 核 4G（而非 4 核 8G）

**清理无用资源：**
- 删除过期测试环境
- 删除未使用的依赖包
- 仅保留近 3 份数据库备份
- 关闭闲置服务

### 5.3 静态资源成本

- 统一存入对象存储（OSS/S3）
- 禁止直接访问存储地址（需通过 CDN 转发）
- 大型媒体文件移至专业存储（视频用 HLS/DASH 分片加载）

### 5.4 缓存与再生策略

**ISR 重新验证时间：**

| 内容类型 | 重新验证频率 |
|----------|-------------|
| **新闻页** | 1 小时 |
| **静态页面** | 1 天 |
| **产品页** | 按需（内容更新时主动触发） |

**CDN 缓存规则：**
- 静态资源用版本号命名
- 更新时变更版本号触发缓存刷新

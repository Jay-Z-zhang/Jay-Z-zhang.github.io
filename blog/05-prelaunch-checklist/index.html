为什么需要这份清单？

我见过太多团队上线后才发现：

  • 监控没配，出了问题不知道
  • 回滚不了，只能硬扛
  • 被攻击了，没有防护
  • 性能太差，用户流失
  • 成本爆炸，预算超标

每一次「上线后才发现」，都是一次本可避免的灾难。

这份清单帮你在上线前发现所有隐患。涵盖 5 大维度、20+ 关键动作。

一、操作卓越性（保障上线与运维流畅）

1.1 事件响应计划

问题： 上线后出了问题，谁处理？怎么升级？

必须明确：

项目内容示例
事件分级P0-P3P0：核心功能不可用；P3：轻微 UI 问题
责任人每个级别对应谁P0 → CTO；P1 → 技术负责人
升级路径一线 → 二线 → 三线运维 → 技术负责人 → 业务负责人
沟通渠道内部 + 外部内部群 + 用户公告页
回滚触发条件什么情况下回滚报错率 > 1%、服务不可用超 5 分钟

为什么重要：

没有事件响应计划 = 出了问题靠吼。谁嗓门大谁指挥，效率极低。

1.2 全链路监控

问题： 你怎么知道系统出了问题？

必须覆盖：

监控类型监控项告警阈值
性能接口响应时间、页面加载速度P99 > 1 秒
错误前端 JS 报错、后端 5xx/4xx5xx > 0.1%
流量QPS 峰值、用户地域分布QPS 突增 > 200%

工具推荐：

  • 前端：Sentry（错误监控）、Lighthouse（性能）
  • 后端：Prometheus + Grafana（指标监控）
  • 全链路：OpenTelemetry（请求追踪）

1.3 部署与回滚能力

问题： 上线后发现问题，能多快回滚？

上线前必须测试：

  • 灰度发布流程：10% 用户先行验证
  • 蓝绿部署流程：新旧版本无缝切换
  • 回滚操作：可在 5 分钟内完成
  • 数据一致性：回滚后数据不受影响

真实案例：

某公司上线新版本后，发现支付接口有 bug。

因为没有回滚流程，只能手动修复代码、重新部署。

耗时 2 小时，期间所有支付失败。

如果有回滚流程：5 分钟解决。

1.4 构建效率优化（Monorepo 场景）

问题： 每次部署都要构建所有模块，耗时太长。

配置项：

  • 依赖包缓存（避免每次下载）
  • 子项目编译结果缓存（只构建变更的模块）
  • 增量构建（只重新构建变更的部分）

目标： 构建时长 ≤ 30 分钟

1.5 域名配置与迁移

检查清单：

  • 添加 www 子域（www.example.com）
  • 设置顶级域名自动重定向到 www（example.com → www.example.com）
  • DNS 零停机迁移（先配新 DNS，等全球生效再停旧的）

二、安全性（防范上线后安全风险）

2.1 Web 应用防火墙（WAF）

问题： 你的网站能抵御常见攻击吗？

必须配置：

防护类型说明配置建议
SQL 注入防止数据库被注入恶意代码开启 WAF 默认规则
XSS防止跨站脚本攻击开启 WAF 默认规则
CSRF防止跨站请求伪造开启 WAF 默认规则
异常流量防止 DDoS 和爬虫单 IP 单日请求 > 1000 次触发挑战

2.2 内容安全策略（CSP）

问题： 你的网站能防止恶意脚本加载吗？

配置示例：

Content-Security-Policy: 
  default-src 'self';
  script-src 'self' https://trusted-cdn.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;

禁止：

  • inline-script（防止内联脚本注入）
  • unsafe-eval（防止 eval 执行恶意代码）

必须添加的安全头：

安全头值作用
X-Frame-OptionsDENY防止点击劫持
X-XSS-Protection1; mode=block开启 XSS 过滤

2.3 环境访问控制

环境访问控制说明
测试/预发密码验证 + 内网 IP 白名单防止未授权访问
生产禁止直接部署需代码评审 + 测试 + 审批

2.4 日志与依赖安全

日志：

  • 对接 ELK/Splunk（集中管理日志）
  • 保留至少 30 天部署日志、访问日志（安全审计需要）

依赖：

  • 提交依赖锁文件（package-lock.json、pom.lock）
  • 配合 Snyk/Dependabot 扫描依赖风险（防止引入有漏洞的依赖）

2.5 合规与权限

SSL/TLS：

  • 证书未过期
  • 域名匹配（泛域名覆盖所有子域）
  • 支持 TLS 1.2+
  • 禁用不安全加密套件

权限：

  • 最小权限原则（开发只操作测试环境，运维只有生产只读权限）
  • 移除离职人员账号
  • 启用 SSO（SAML/OAuth2.0）
  • 操作审计日志（跟踪权限变更、部署操作）

Cookie 合规：

  • 禁用不必要的第三方 Cookie
  • 标记必要 Cookie 用途
  • 符合 GDPR/CCPA

2.6 防范滥用

  • 核心接口（登录、支付）实施速率限制（单用户 1 分钟 ≤ 10 次）
  • 多租户应用添加「滥用举报入口」
  • 后台可快速处理（封禁账号、删除内容）

三、可靠性（避免上线后服务中断）

3.1 冗余与故障切换

问题： 如果某个服务器挂了，服务会中断吗？

核心服务：

  • 多区域节点部署（至少 2 个区域）
  • 自动故障切换（某区域不可用 → 流量自动路由到其他区域）

数据库/缓存：

  • 主从架构或集群模式（避免单点故障）
  • 测试主从切换有效性（主节点宕机后，从节点 10 秒内接管）

3.2 缓存策略

资源类型缓存策略说明
静态资源（图片/CSS/JS）长期缓存（max-age=31536000）+ CDN一年有效期
API 响应根据更新频率实时数据不缓存、半实时缓存 5 分钟
静态页面ISR（定时重新生成）新闻详情页 1 小时重新验证
动态数据接口缓存用户个人信息

3.3 可观测性

分布式跟踪：

  • 接入 OpenTelemetry
  • 串联前端 → API → 数据库的请求链路
  • 可定位跨服务的性能瓶颈或错误

负载测试：

  • 模拟 QPS 达预期峰值的 1.5 倍
  • 验证上游服务承载能力
  • 避免上线后因流量突增崩溃

四、性能优化（提升用户体验）

4.1 核心性能指标

前端（Core Web Vitals）：

指标目标说明工具
LCP≤ 2.5 秒最大内容绘制时间Lighthouse
FID≤ 100 毫秒首次输入延迟Sentry
CLS≤ 0.1累积布局偏移Lighthouse

后端（TTFB）：

接口类型目标说明
核心接口≤ 300 毫秒首页数据接口等
非核心接口≤ 500 毫秒设置页、帮助页等

4.2 资源加载优化

图像：

  • 压缩体积（TinyPNG）
  • 响应式尺寸（移动端 500px，PC 端 1000px）
  • WebP/AVIF 格式（比 JPG 小 30-50%）
  • 非首屏图像延迟加载（loading="lazy"）

脚本：

  • 代码拆分（路由懒加载）
  • 按需加载非首屏脚本
  • 禁用无意义第三方脚本
  • 添加 defer/async 属性

字体：

  • 字体子集（仅包含应用所需字符）
  • 预加载关键字体
  • font-display: swap 避免 FOIT（无字体显示）

4.3 降低网络延迟

  • 核心服务部署区域与目标用户匹配
  • 避免多层代理（CDN → API 网关 → 后端）
  • 必要时直接对接核心服务

五、成本优化（避免资源浪费）

5.1 成本构成梳理

资源类型监控项告警阈值
服务器实例CPU/内存使用率> 80%
CDN 流量月流量、峰值带宽月流量超预算 10%
对象存储存储容量、请求次数存储超预算 10%
数据库连接数、慢查询慢查询 > 1 秒

设置成本告警： 月度支出超预算 10% 时触发通知

5.2 计算与存储优化

计算资源：

  • 非核心接口超时设为 3 秒（避免资源占用过久）
  • 低流量服务用 2 核 4G（而非 4 核 8G）

清理无用资源：

  • 删除过期测试环境
  • 删除未使用的依赖包
  • 仅保留近 3 份数据库备份
  • 关闭闲置服务

5.3 静态资源成本

  • 统一存入对象存储（OSS/S3）
  • 禁止直接访问存储地址（需通过 CDN 转发）
  • 大型媒体文件移至专业存储（视频用 HLS/DASH 分片加载）

5.4 缓存与再生策略

ISR 重新验证时间：

内容类型重新验证频率说明
新闻页1 小时内容更新频繁
静态页面1 天内容基本不变
产品页按需内容更新时主动触发

CDN 缓存规则：

  • 静态资源用版本号命名（app.v1.2.3.js）
  • 更新时变更版本号触发缓存刷新

上线前最终检查

□ 事件响应计划已制定
□ 全链路监控已配置
□ 灰度/蓝绿/回滚流程已测试
□ WAF + CSP 已部署
□ 日志持久化已配置
□ SSL 证书已验证
□ 权限已梳理
□ 数据库主从已测试
□ 缓存策略已配置
□ 负载测试已通过
□ Core Web Vitals 达标
□ 成本告警已设置
□ 无用资源已清理

一句话总结

上线前的每一分钟检查，都能避免上线后的每一小时救火。

延伸推荐

  • LTV/CAC > 3？ — 上线后怎么衡量获客效率
  • 增长指标体系搭建 — 上线后该关注哪些指标
  • 海外推广渠道全攻略 — 上线后怎么获客
